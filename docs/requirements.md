# Relay MVP 要件

## 対象業務

機能実装によって複数コンポーネントに発生した変更を一つのリリースへ編成し、PR、migration、依存関係、停止要否、反映順序、検証条件を確定して実行可能な計画にする。

## 情報構造

グローバルナビゲーションには、独立して管理するドメインオブジェクトだけを置く。

- リリース
- チーム
- コンポーネント

一つのリリースを選択した後、そのリリースに従属するビューを表示する。

- 変更
- 依存マップ
- 実行計画
- 検証

実行計画や検証を、リリースと同じ階層の管理対象として扱わない。

依存マップはコンポーネント変更間の構造を確認するビューとし、実行計画はその依存関係から導出された実施順序、並列実行、検証条件、リスクを確認するビューとする。

## 基本フロー

1. 管理者がチーム一覧とコンポーネント一覧から、それぞれを登録する。
2. リリース責任者が機能変更を作成する。
3. 機能変更に、コンポーネントごとの変更を追加する。
4. 各変更へ担当チーム、PR、migration、依存先、反映方法、回復方法を登録する。
5. サービスが停止・メンテナンスモード要否と、実行可能な順序を評価する。
6. 各変更の検証内容、実施条件、予定、担当を登録する。
7. すべての依存・検証ゲートが成立する実行計画を確定する。
8. 実行時は計画順序と検証結果に基づいて次工程への遷移を制御する。

## マスタ

### チーム

- 名称
- 責任者
- メンバー
- 担当コンポーネント
- 連絡・エスカレーション先

### コンポーネント

- 名称: iOS、Android、バックエンド、管理画面など
- 種別: モバイルアプリ、Web API、Webアプリ、バッチなど
- 担当チーム
- リポジトリ
- 配布・デプロイ特性
- 標準的な検証方法
- 標準的な回復方法

## リリース

- リリースID、名称、責任者、予定日時、状態
- 起点となる一つ以上の機能変更
- コンポーネント変更
- 実行計画
- 検証計画
- Go/No-Go判定

## 機能変更

ユーザーまたは業務へ提供する変更の単位。複数コンポーネント変更を束ねる。

- 機能変更ID、名称、目的
- リリース予定
- 公開方法
- Feature Flag
- コンポーネント変更一覧

## コンポーネント変更

同一コンポーネントの変更はコンポーネント単位にグルーピングする。複数PRが同じコンポーネントの一つのバージョン遷移へ含まれる場合、バージョン計画をPRごとに重複して保持しない。

- 対象コンポーネント
- 担当チーム
- 変更内容
- 関連PR（一つ以上を許容）
- ベース／リリース対象のrevision
- 依存する別のコンポーネント変更または外部条件
- migrationの有無、方式、互換性、所要時間、失敗時対応
- 停止またはメンテナンスモードの要否と理由
- デプロイ／配布方法と予定
- Feature Flagの操作
- rollback / roll-forward方法
- 必要な検証

## コンポーネント別バージョン計画

- 現在バージョンと変更後バージョン
- 即時切替、段階切替、ストア段階配信
- 切替開始と100%到達予定
- 配信率のマイルストーン
- 新旧バージョンの共存可否とFeature Flag
- 旧API・旧schemaを維持する期限
- contract migrationを開始できる条件
- バージョン別エラー率と配信停止条件
- 識別子の取得元。モバイルはストア、バックエンド・Webはデプロイ環境またはCI artifactを基本とする

バックエンド・Webの「バージョン」はアプリ版ではなく、本番で現在稼働しているrevision / artifactと、変更後に稼働させるrevision / artifactを指す。

## 承認・予定

- 実行状態とは別に、未申請、承認待ち、承認済み、差し戻しの承認状態を持つ
- リリース予定は日付だけでなく時刻を持ち、実行計画の基準時刻とする
- 予定の考慮事項と備考を保持する
- 予定変更、承認変更、備考変更について、変更者、変更時刻、変更内容、理由を履歴として保持する
- 入力訂正など監査対象にしない操作では、保存時に履歴へ残さない選択を許可する

## migrationと停止判定

migrationがある場合、少なくとも以下を入力・評価する。

- expand / migrate / contract の段階
- online / blocking
- 新旧コードの同時稼働可否
- backward / forward compatibility
- 想定所要時間とロック範囲
- rollback可能地点

停止・メンテナンスモードは手入力のチェック項目ではなく、これらの事実と依存関係から候補を判定する。Jevは `停止なし / メンテナンスモード / サービス停止 / 判定不能` の型付き選択に利用できる。ルール違反や入力不足は決定的な検証で拒否する。

## 検証

- 対象: PR、コンポーネント変更、migration、リリース
- 検証内容
- 実施担当チーム
- 実施可能になる条件
- 予定時刻または時間枠
- 成功条件
- 失敗時の停止条件
- 証拠URLまたは結果

## 実行計画グラフ

グラフは組織図ではなく、リリース実行の因果関係を表す。

### ノード

- 機能変更
- コンポーネント変更
- PR
- migration
- デプロイ／ストア公開
- Feature Flag操作
- 検証
- 待機条件

チームとコンポーネントは各ノードの所有・対象属性として表示し、必要な場合にフィルタ軸として使う。

### エッジ

- `含む`
- `実装する`
- `反映前に必要`
- `完了後に検証`
- `成功時に進行可能`
- `失敗時に停止／回復`

### 必須表示

- コンポーネント別のレーン
- 担当チーム
- PR番号
- migration
- 反映予定
- 検証工程
- ストア審査や段階公開などの待機条件
- クリティカルパス
- 停止・メンテナンスモード要否

## MVP受け入れ条件

1. UIからチームとコンポーネントを登録できる。
2. 一つの機能変更へiOS、Android、バックエンド、管理画面の変更を追加できる。
3. 各変更にPR、migration、依存、停止要否、反映予定、検証を登録できる。
4. バックエンドのmigrationとモバイル公開を含む順序をグラフで確認できる。
5. migration情報から停止なし・メンテナンス・停止・判定不能を評価できる。
6. 検証の担当、実施条件、予定、状態を一覧で確認できる。
7. 依存または検証条件が未成立なら、その工程以降を開始できない。

## Webアプリケーション要件

- リリース一覧、リリース詳細の各タブ、チーム、コンポーネントは固有URLを持つ。
- ブラウザの戻る・進む、再読み込み、URLからの直接表示が機能する。
- リリース、チーム、コンポーネント、コンポーネント変更を作成・参照・編集・削除できる。
- 入力内容は再読み込み後も保持する。
- リリースまたはコンポーネントから参照されているチームは削除できない。
- リリース変更から参照されているコンポーネントは削除できない。
- リリース詳細を閉じた場合はリリース一覧へ戻る。
